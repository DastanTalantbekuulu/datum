**Ответственность:** Предоставление всей географической информации: стран, регионов, городов, валют и телефонных кодов.

*   **Владеет таблицами:**
    *   `country`
    *   `currency`
    *   `country_currency`
    *   `phone_code`
    *   `region`
    *   `city`

*   **Зависимости:** Нет.

*   **Почему так?** Географические данные — это отдельный, самодостаточный домен. Он может использоваться не только для профилей пользователей, но и, например, для логистики, аналитики и т.д.

#### 4. Person Service
**Ответственность:** Управление всеми данными, связанными с физическим лицом: ФИО, дата рождения, гражданство, документы, адреса и семейные связи.

*   **Владеет таблицами:**
    *   `person`
    *   `identity_document`
    *   `address` (адрес тесно связан с человеком)
    *   `person_relation`

*   **Зависимости:**
    *   От **Dictionary Service** для получения данных о поле (`gender`) и типах отношений (`relation_type`).
    *   От **Geo Service** для получения информации о стране гражданства (`citizenship_id`) и городе адреса (`city_id`).

*   **Почему так?** "Личность" или "Профиль" — это центральный домен, который объединяет персональные данные. Этот сервис будет основным источником информации о человеке для других частей системы.

---

#### 5. Contact Service
**Ответственность:** Управление всеми способами связи с сущностями (людьми, пользователями). Хранит "чистые" email и телефон, а также их привязку к конкретным лицам или пользователям.

*   **Владеет таблицами:**
    *   `phone`
    *   `email`
    *   `email_domain`
    *   `person_phone`
    *   `person_email`
    *   `user_phone`
    *   `user_email`

*   **Зависимости:**
    *   От **Dictionary Service** для получения типов контактов (`contact_type`).
    *   От **Geo Service** для получения телефонных кодов (`phone_code`).
    *   От **Person Service** (для привязки контактов к `person_id`).
    *   От **Auth Service** (для привязки контактов к `user_id`).

*   **Почему так?** Контактная информация — это универсальная концепция. Выделив ее в отдельный сервис, мы получаем переиспользуемый компонент. Например, если в будущем появятся "Компании", мы сможем легко добавить `company_phone` и `company_email`, не изменяя `Person Service`.

#### 6. File Service
**Ответственность:** Хранение метаданных файлов и управление ими (загрузка, скачивание, удаление). Предоставляет доступ к файлам по уникальному идентификатору.

*   **Владеет таблицами:**
    *   `storage_file`
    *   `person_photo`

*   **Зависимости:**
    *   От **Dictionary Service** для получения типов фотографий (`photo_type`).
    *   От **Person Service** (для привязки фотографий к `person_id`).

*   **Почему так?** Управление файлами — это отдельная инфраструктурная задача. Этот сервис может заниматься оптимизацией хранения, созданием превью, проверкой на вирусы и т.д., не перегружая бизнес-логику других сервисов.

### Ключевые соображения и вызовы при переходе

1.  **Уничтожение внешних ключей (Foreign Keys) между сервисами.**
    *   В монолите у вас есть `users.person_id BIGINT UNIQUE REFERENCES person (id)`. В микросервисной архитектуре такой FK на уровне БД невозможен.
    *   **Решение:** Эта связь поддерживается на уровне приложения.
        *   При создании пользователя `Auth Service` делает API-вызов в `Person Service` для создания профиля и получает `person_id`.
        *   Или, наоборот, при создании профиля в `Person Service` инициируется создание пользователя в `Auth Service`.
        *   Транзакционность здесь достигается с помощью паттернов **Saga** или **Two-Phase Commit (2PC)**, но чаще всего — через компенсирующие транзакции в рамках Saga.

2.  **Избыточность данных (Data Duplication).**
    *   Чтобы уменьшить количество межсервисных вызовов, некоторые данные можно дублировать.
    *   **Пример:** `Person Service` при отображении профиля может хранить `country_name` (из `Geo Service`) или `gender_name` (из `Dictionary Service`) прямо в своей таблице `person` (в денормализованном виде). Эти данные должны обновляться через события (events), когда они меняются в сервисе-источнике. Это trade-off между консистентностью и производительностью.

3.  **Обеспечение целостности данных.**
    *   В монолите база данных следит за целостностью. В микросервисах за это отвечает код.
    *   **Пример:** Удаление `person` должно каскадно "удалить" (или пометить как удаленные) все связанные сущности в других сервисах (контакты, фотографии, адреса). Это также реализуется через событийную архитектуру: `Person Service` публикует событие `PersonDeleted`, а другие сервисы на него подписываются и выполняют нужные действия.

4.  **Коммуникация между сервисами.**
    *   **Синхронная:** REST/gRPC вызовы, когда нужен немедленный ответ (например, при создании пользователя).
    *   **Асинхронная:** Брокеры сообщений (RabbitMQ, Kafka) для событий, которые не требуют немедленной реакции (например, `PersonUpdated`, `NewPhotoUploaded`). Это повышает отказоустойчивость и производительность системы.

### Заключение

Предложенное разбиение — это отправная точка. Оно создает четкие границы ответственности, что позволяет командам работать над разными сервисами независимо, использовать разные технологии и масштабировать только те части системы, которые в этом нуждаются. Главный компромисс — это усложнение архитектуры и необходимость управления распределенными транзакциями и консистентностью данных на уровне приложения.

### Два подхода

#### 1. Межсервисные вызовы (API Composition)

**Идея:** "Единственный источник правды" (Single Source of Truth). Данные хранятся только в том сервисе, который за них отвечает. Если другому сервису нужны эти данные, он делает синхронный API-вызов (например, REST или gRPC) в сервис-владелец.

*   **Как это работает:**
    *   `Person Service` хранит только `citizenship_id` (ID страны).
    *   Когда нужно отобразить профиль пользователя, клиент (или API Gateway) сначала запрашивает данные из `Person Service`, получает `citizenship_id`.
    *   Затем он делает второй вызов в `Geo Service` с этим `citizenship_id`, чтобы получить название страны (`name_en`, `i18n` и т.д.).
    *   Данные "собираются" на лету.

*   **Целостность данных:**
    *   **Высокая (Strong Consistency):** Вы всегда получаете самые актуальные данные прямо из источника. Нет риска получить устаревшее название страны.
    *   **Хрупкость:** Если `Geo Service` недоступен, вы не сможете отобразить название страны. Профиль пользователя будет неполным. Целостность есть, но доступность данных страдает.

#### 2. Дублирование данных (Denormalization / Caching)

**Идея:** Для ускорения чтения и повышения отказоустойчивости, скопировать (дублировать) часто используемые данные из одного сервиса в другой.

*   **Как это работает:**
    *   `Person Service` хранит не только `citizenship_id`, но и дублирует поля: `citizenship_name`, `citizenship_iso2`.
    *   Когда нужно отобразить профиль, все данные получаются из одного сервиса (`Person Service`) за один запрос. Это очень быстро.

*   **Целостность данных:**
    *   **Низкая (Eventual Consistency):** Данные могут быть временно неактуальными. Если в `Geo Service` изменится название страны, в `Person Service` оно останется старым до тех пор, пока не будет обновлено.
    *   **Как обеспечить целостность?** Через **асинхронную событийную шину** (Event Bus, например, Kafka, RabbitMQ).
        1.  В `Geo Service` изменяют название страны.
        2.  `Geo Service` публикует событие `CountryUpdated` с новой информацией (ID, старое название, новое название).
        3.  `Person Service` подписан на это событие. Получив его, он находит всех людей с `citizenship_id` и обновляет у себя дублирующие поля (`citizenship_name` и т.д.).
    *   **Результат:** Система в конечном итоге придет в консистентное состояние. Между изменением и обновлением есть задержка.

### Целостность данных: Глубокий анализ

Это главный пункт вашего вопроса. Целостность — это не только "правильность" данных, но и их "доступность" и "актуальность".

*   **При вызовах:** вы жертвуете **доступностью** ради **актуальности**. Если `Geo Service` упал, целостность всей системы нарушена, потому что часть данных недоступна.
*   **При дублировании:** вы жертвуете **актуальностью** ради **доступности**. Система остается работоспособной, но данные могут быть временно неверными.

**Как управлять целостностью при дублировании?**

1.  **События (Events):** Основа всего. Источник данных публикует события о своих изменениях (`Created`, `Updated`, `Deleted`).
2.  **Идемпотентность:** Обработчик событий в сервисе-потребителе должен быть идемпотентным. Если одно и то же событие `CountryUpdated` придет дважды (из-за сбоя в сети), результат не должен измениться.
3.  **Механизмы повтора (Retries):** Если `Person Service` не смог обработать событие (например, был перезапущен), брокер сообщений должен попытаться доставить его снова.
4.  **Процессы согласования (Reconciliation):** Периодически (например, раз в ночь) можно запускать фоновые задачи, которые сверяют данные между сервисами и исправляют расхождения. Это "сетка безопасности" на случай потери событий.

### Гибридный подход: Как выбрать?

В реальных проектах почти никогда не используют что-то одно. Выбор зависит от конкретного типа данных и бизнес-требований.

#### Используйте **межсервисные вызовы**, когда:

*   **Данные меняются часто.** Дублирование приведет к огромному потоку событий и постоянным рассинхронам.
*   **Требуется 100% актуальность.** Например, при проверке баланса счета или доступности товара на складе.
*   **Данные используются редко.** Нет смысла дублировать то, что нужно раз в год.
*   **Пример:** `identity_document`. При проверке документа нужно всегда обращаться к `Person Service`, чтобы получить самую свежую информацию о его действительности (`is_active`, `expiry_date`).

#### Используйте **дублирование данных**, когда:

*   **Операция чтения dominates (Read-heavy).** Данные читаются в 100-1000 раз чаще, чем пишутся.
*   **Данные меняются редко.** Справочники, такие как страны, валюты, роли.
*   **Латентность критична для UI.** Пользователь не должен ждать, пока подгрузится название города или страны.
*   **Нужна высокая доступность.** Профиль пользователя должен отображаться, даже если `Geo Service` упал.
*   **Пример:** `person.citizenship_id`. Название страны — идеальный кандидат для дублирования. Оно меняется крайне редко, а читается постоянно.

### Практический пример из вашей схемы

**Задача:** Отобразить профиль человека с его гражданством и городом проживания.

**Решение с дублированием (рекомендуемый вариант для UI):**

1.  **Таблица `person` в `Person Service`:**
    ```sql
    CREATE TABLE person (
        -- ... поля
        citizenship_id BIGINT REFERENCES country (id) ON DELETE SET NULL,
        citizenship_name VARCHAR(100), -- ДУБЛИРОВАНО
        citizenship_iso2 CHAR(2),      -- ДУБЛИРОВАНО

        city_id BIGINT REFERENCES city (id) ON DELETE SET NULL,
        city_name VARCHAR(100),        -- ДУБЛИРОВАНО
        region_name VARCHAR(100),      -- ДУБЛИРОВАНО
        -- ...
    );
    ```
2.  **Процесс:**
    *   При создании/обновлении человека, `Person Service` делает **один вызов** в `Geo Service`, чтобы получить актуальные данные по `citizenship_id` и `city_id`, и сохраняет их у себя.
    *   `Geo Service` при изменении страны/города публикует события `CountryUpdated`/`CityUpdated`.
    *   `Person Service` на эти события подписывается и обновляет дублирующие поля у всех затронутых людей.
3.  **Результат:** UI делает один запрос в `Person Service` и мгновенно получает готовый профиль.

### Преимущества этого подхода (почему он хорош)

1.  **Максимальная производительность:** Доступ к справочникам — это просто обращение к объекту в памяти. Это самый быстрый способ, который возможен. Идеально для высоконагруженных систем, где каждый микросекунд на счету.
2.  **Высочайшая доступность:** После успешного старта потребительский сервис **полностью независим** от `Dictionary Service`. Даже если `Dictionary Service` упадет, все остальные сервисы продолжат работать корректно со своими справочниками.
3.  **Простота для потребителя:** Логика на стороне клиента тривиальна: "при старте скачай, положи в память". Не нужны сложные CDC-коннекторы, брокеры сообщений, обработка инкрементальных обновлений.
4.  **Удобство работы с i18n:** Весь пакет содержит все переводы. Сервису не нужно делать дополнительные запросы для локализации данных. Он просто берет нужную языковую ветку из уже загруженного объекта.
5.  **Атомарность и консистентность:** Сервис получает снепшот всех справочников в консистентном состоянии. Не бывает ситуации, когда `country` обновился, а `currency` еще нет.

### Недостатки и компромиссы (цена вопроса)

1.  **"Консистентность при перезапуске" (Restart Consistency):** Это главный недостаток. Данные не обновляются в реальном времени. Чтобы изменения вступили в силу, требуется перезапуск сервисов.
    *   **Вопрос к бизнесу:** "Готовы ли мы мириться с тем, что для добавления новой роли в системе потребуется перезапуск всех сервисов?" Для справочников, которые меняются раз в год, это нормально. Для сущностей, которые меняются каждый день — нет.
2.  **Зависимость от `Dictionary Service` при старте:** Сервис не сможет запуститься, если `Dictionary Service` (или файловое хранилище, где лежит пакет) будет недоступен. Это нужно учесть в стратегиях развертывания (например, использовать health checks).
3.  **Потребление памяти:** Если справочники станут очень большими (миллионы записей), загрузка их всех в память в каждом сервисе может стать проблемой. Для вашего текущего набора данных это не является проблемой.

### Способ 2: Вебхуки (Push-уведомления) — Сбалансированный

**Идея:** `Dictionary Service` не ждет, пока его спросят. Он сам "говорит" другим сервисам, что данные изменились.

**Как это работает:**

1.  **Регистрация:** При старте каждый потребительский сервис регистрирует свой "вебхук-URL" в `Dictionary Service`.
    `POST /api/v1/webhooks/register` -> `{ "url": "http://person-service/internal/dictionaries/reload" }`

2.  **Оповещение:** Когда администратор меняет данные в `Dictionary Service`, тот пробегается по списку зарегистрированных URL и отправляет им POST-запрос (например, с пустым телом).

3.  **Перезагрузка:** Получив такой запрос, потребительский сервис запускает свою процедуру перезагрузки справочников (ту же `reloadDictionary()` из примера выше).

*   **Плюсы:**
    *   **Мгновенно:** Изменения применяются почти в реальном времени.
    *   **Эффективно:** Нет лишнего трафика, когда ничего не меняется.
*   **Минусы:**
    *   **Сложность:** Нужно реализовать механизм регистрации, хранения URL и их оповещения.
    *   **Хрупкость:** Что если потребительский сервис был недоступен в момент отправки вебхука? `Dictionary Service` должен реализовывать логику повторных попыток (retry).

### Способ 3: Брокер сообщений (Pub/Sub) — Самый надежный

**Идея:** Использовать промежуточное звено — брокер сообщений (RabbitMQ, Kafka). `Dictionary Service` публикует событие, а все заинтересованные сервисы его "слушают".

**Как это работает:**

1.  `Dictionary Service` после изменения данных публикует сообщение в общий топик/очередь (например, `dictionaries.updated`).
2.  Все остальные сервисы подписаны на этот топик.
3.  Получив сообщение, они запускают свою процедуру перезагрузки.

*   **Плюсы:**
    *   **Надежность:** Брокер гарантирует доставку сообщения. Если сервис был "офлайн", он получит сообщение после перезапуска.
    *   **Полная развязка:** `Dictionary Service` ничего не знает о потребителях. Он просто "кричит" в пустоту, а его слушают те, кому это нужно.
*   **Минусы:**
    *   **Сложность инфраструктуры:** Требует установки, настройки и поддержки брокера сообщений. Это серьезный компонент.

**Как это работает:**

**Почему именно так?**
*   **Производительность:** Обращение к памяти в тысячи раз быстрее, чем запрос к БД или другому сервису. Для UI это критично.
*   **Доступность:** Сервисы не зависят от `Dictionary Service` во время работы.
*   **Единообразие:** Это тот же паттерн, что и для справочников. Не нужно изобретать велосипед.

#### Сценарий Б: Динамические уведомления для пользователей

Это персональные сообщения, которые генерируются системой в ответ на какие-то события: "Ваш заказ #12345 отправлен", "Вам пришло новое приглашение в друзья", "Иван Иванов прокомментировал вашу запись".

*   **Хранение: Исключительно в БД.**
*   **Ответственность: Отдельный микросервис (например, `Notification Service`).**

**Как это работает:**
1.  Эти сообщения — это полноценные сущности с жизненным циклом: созданы -> прочитаны -> удалены/архивированы.
2.  Они привязаны к конкретным пользователям.
3.  Их может быть миллионы. Хранить их всех в памяти каждого сервиса невозможно и не нужно.
4.  Создается `Notification Service`, который владеет таблицей `message` (или `notification`).
5.  Другие сервисы (например, `Order Service`) не создают сообщения напрямую. Они публикуют событие `OrderShippedEvent`.
6.  `Notification Service` подписан на это событие, получает его, создает соответствующее сообщение в своей БД и привязывает его к нужному пользователю.
7.  Фронтенд (или мобильное приложение) делает запрос в `Notification Service` (`GET /api/v1/notifications?unread=true`) для получения списка сообщений для текущего пользователя.

**Почему именно так?**
*   **Персистентность:** Сообщения не должны пропасть при перезапуске сервиса.
*   **Масштабируемость:** База данных отлично справляется с хранением и запросами больших объемов данных.
*   **Состояние:** У сообщений есть состояние (прочитано/не прочитано), которое нужно надежно хранить.
*   **Разделение ответственности:** Бизнес-логика уведомлений выносится в отдельный сервис.

### 2. Сущность `i18n` (международные данные)

`i18n` — это не совсем сущность, а скорее **структура данных**, содержащая переводы.

*   **Хранение: Гибридный подход.**
    *   **Источник правды и редактирование: В БД `Dictionary Service`.**
    *   **Использование в рантайме: В памяти сервисов-потребителей.**

**Почему именно так?**
1.  **Источник правды в БД:** Переводы должны быть редактируемыми. Администратор должен иметь возможность зайти в админку `Dictionary Service` и исправить опечатку в переводе или добавить новый язык. Хранить их только в коде или в памяти — значит лишить себя этой гибкости. База данных — единственное надежное место для персистентности и управления.

2.  **Использование в памяти:** Как мы уже выяснили со статичными сообщениями и справочниками, обращение к переводам — это очень частая операция. Делать для каждого UI-элемента запрос в БД или по сети — это убить производительность. Поэтому вся "пачка" переводов кэшируется в памяти.

**Это идеальный пример паттерна "Command Query Responsibility Segregation" (CQRS) в миниатюре:**
*   **Команды (запись):** Редактирование переводов происходит в `Dictionary Service` (его БД).
*   **Запросы (чтение):** Чтение переводов для отображения происходит из локального in-memory кэша в каждом сервисе.

### Шаг 2: Универсальная модель данных в БД

Чтобы хранить данные, описанные в такой гибкой схеме, обычные таблицы (`country`, `role`) не подойдут. Нам нужна **EAV-модель (Entity-Attribute-Value)** или похожая структура.

Вот простая и эффективная схема из 3-х таблиц:

```sql
-- 1. Справочники (описывает сущности из YAML)
CREATE TABLE dictionary_entity (
    id SERIAL PRIMARY KEY,
    entity_name VARCHAR(100) NOT NULL UNIQUE -- 'country', 'role', 'ui_text'
);

-- 2. Атрибуты (описывает поля из YAML)
CREATE TABLE dictionary_attribute (
    id SERIAL PRIMARY KEY,
    entity_id INT NOT NULL REFERENCES dictionary_entity(id),
    attribute_name VARCHAR(100) NOT NULL, -- 'iso_alpha2', 'role'
    attribute_type VARCHAR(50) NOT NULL,  -- 'string', 'boolean', 'json'
    CONSTRAINT uq_entity_attribute UNIQUE (entity_id, attribute_name)
);

-- 3. Значения (содержит сами данные)
CREATE TABLE dictionary_value (
    entity_id INT NOT NULL REFERENCES dictionary_entity(id),
    item_id BIGINT NOT NULL,      -- ID конкретной записи (например, ID страны)
    attribute_id INT NOT NULL REFERENCES dictionary_attribute(id),
    value_text TEXT,
    value_timestamp TIMESTAMPTZ,
    value_boolean BOOLEAN,
    value_json JSONB,
    CONSTRAINT pk_dictionary_value PRIMARY KEY (entity_id, item_id, attribute_id)
);
```

**Как это работает:**
*   При старте сервис читает `dictionaries_schema.yaml`.
*   Он создает записи в `dictionary_entity` и `dictionary_attribute` на основе YAML.
*   Все данные (например, `iso_alpha2: 'US'`) хранятся в `dictionary_value`.

### Как это работает: Стратегия хранения

Теперь ваш сервис должен уметь обрабатывать обе стратегии.

1.  **При запуске:** Сервис читает `dictionaries_schema_v3.yaml`.
2.  **Для `country` (стратегия `separate_table`):**
    *   Сервис генерирует и выполняет SQL: `CREATE TABLE country (...)`.
    *   Данные для этого справочника будут храниться в этой новой таблице.
3.  **Для `product_attribute` (стратегия `eav_shared_table`):**
    *   Сервис **не создает новую таблицу**. Он использует заранее созданную универсальную таблицу (ту самую EAV-модель из предыдущего ответа).
    *   При сохранении данных для `product_attribute`, сервис будет писать в эту универсальную таблицу, указывая `entity_name = 'product_attribute'`.

**Когда использовать какую стратегию?**

*   **`separate_table` (99% случаев):**
    *   Все стандартные справочники (`country`, `role`, `currency`, `language`).
    *   Любые данные, где набор полей более-менее стабилен и известен заранее.
    *   Когда важна производительность чтения и целостность данных.

*   **`eav_shared_table` (редкие, специфические случаи):**
    *   Каталоги товаров с тысячами уникальных характеристик.
    *   Системы опросов, где каждый опрос может иметь свои уникальные поля.
    *   Когда гибкость добавления новых полей без миграции БД важнее производительности.

### Как решать связи (Foreign Keys)?

В NoSQL связи чаще всего решаются **денормализацией**.

**Пример:** Вам нужно получить страну и ее валюты.

*   **SQL-подход (JOIN):**
    ```sql
    SELECT c.*, cur.code, cur.symbol
    FROM country c
    JOIN country_currency cc ON c.id = cc.country_id
    JOIN currency cur ON cc.currency_code = cur.code;
    ```
*   **NoSQL-подход (Denormalization):**
    Вы просто встраиваете (embed) данные о валюте прямо в документ страны.

    **Коллекция `countries` (денормализованная):**
    ```json
    {
      "_id": ObjectId("..."),
      "iso_alpha2": "US",
      "iso_alpha3": "USA",
      "currencies": [ // Массив встроенных объектов
        { "code": "USD", "symbol": "$" }
      ],
      "i18n": { "en": { "name": "United States" } }
    }
    ```

### Вариант 1: Генерация и отправка байт-кода в рантайме (Ваша идея)

Это самый амбициозный и "магический" подход.

#### Как это могло бы работать:

1.  **Клиент запрашивает модель:** `Person Service` при старте делает запрос на `GET /api/v1/models/Country.class`.
2.  **Сервер генерирует байт-код:** `Dictionary Service` на основе схемы `country` использует библиотеку типа **ASM** или **Byte Buddy** для генерации Java-класса в виде массива байт.

4.  **Клиент загружает класс:** `Person Service` получает байты и загружает их в свой JVM с помощью кастомного `ClassLoader`.

#### Почему это почти всегда плохая идея (Критические проблемы):

1.  **Ад класслоадера (ClassLoader Hell):** Это главная проблема. Что произойдет, когда схема `country` обновится до версии 2?

    *   Вам придется создавать новый `ClassLoader` для каждой версии модели. Это быстро приводит к утечкам памяти и `ClassCastException`, когда вы пытаетесь передать объект `Country v1` в метод, ожидающий `Country v2`.
2.  **Безопасность:** Это огромная дыра в безопасности. Если `Dictionary Service` будет скомпрометирован, он сможет разослать всем клиентам вредоносный байт-код, который будет выполнен в их JVM. Требуется сложнейшая инфраструктура цифровой подписи кода.
3.  **Сложность отладки:** Отлаживать код, которого нет в исходниках, — это кошмар. Стектрейсы будут непонятными.
4.  **Привязка к технологии:** Этот подход работает только для JVM. Что делать, если у вас появится сервис на Python или Go? Для каждого языка нужно будет писать свой генератор и свой механизм загрузки.

**Вердикт:** Технически интригующая, но на практике крайне опасная и неподдерживаемая архитектура. Избегайте ее.

```java
@RestController
@RequestMapping("/api/v1/schemas")
@RequiredArgsConstructor
public class SchemaExportController {

    private final MongoTemplate mongoTemplate;
    private final ObjectMapper objectMapper;

    @GetMapping(value = "/{dictName}/json-schema", produces = MediaType.APPLICATION_JSON_VALUE)
    public ResponseEntity<String> getJsonSchema(@PathVariable String dictName) {
        // 1. Загружаем вашу внутреннюю схему из MongoDB
        DictionarySchema internalSchema = mongoTemplate.findOne(
            Query.query(Criteria.where("_id").is(dictName)),
            DictionarySchema.class,
            "dictionaries_schema"
        );

        if (internalSchema == null) {
            return ResponseEntity.notFound().build();
        }

        // 2. Трансформируем вашу схему в JSON Schema
        JsonNode jsonSchema = convertToJsonSchema(dictName, internalSchema.getDefinition());

        // 3. Отдаем результат
        return ResponseEntity.ok(jsonSchema.toString());
    }

    private JsonNode convertToJsonSchema(String dictName, DictionaryDefinition definition) {
        // Здесь происходит магия преобразования вашей схемы в JSON Schema
        ObjectNode schema = objectMapper.createObjectNode();
        schema.put("$schema", "http://json-schema.org/draft-07/schema#");
        schema.put("title", capitalize(dictName));
        schema.put("type", "object");

        ObjectNode properties = schema.putObject("properties");
        ArrayNode required = schema.putArray("required");

        for (Map.Entry<String, FieldDefinition> entry : definition.getFields().entrySet()) {
            String fieldName = entry.getKey();
            FieldDefinition fieldDef = entry.getValue();

            ObjectNode fieldSchema = properties.putObject(fieldName);
            mapType(fieldSchema, fieldDef.getType()); // Преобразуем наш тип в JSON Schema тип

            if (fieldDef.isRequired()) {
                required.add(fieldName);
            }
        }
        return schema;
    }

    private void mapType(ObjectNode fieldSchema, String internalType) {
        switch (internalType) {
            case "string":
                fieldSchema.put("type", "string");
                break;
            case "boolean":
                fieldSchema.put("type", "boolean");
                break;
            case "object":
                fieldSchema.put("type", "object");
                fieldSchema.put("additionalProperties", true);
                break;
            // ... добавьте другие типы: integer, number, date, etc.
            default:
                fieldSchema.put("type", "string"); // fallback
        }
    }
    
    private String capitalize(String str) {
        return str.substring(0, 1).toUpperCase() + str.substring(1);
    }
}

import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.github.victools.jsonschema.generator.Option;
import com.github.victools.jsonschema.generator.OptionPreset;
import com.github.victools.jsonschema.generator.SchemaGenerator;
import com.github.victools.jsonschema.generator.SchemaGeneratorConfig;
import com.github.victools.jsonschema.generator.SchemaVersion;
import com.github.victools.jsonschema.module.jackson.JacksonModule;
import org.springframework.web.client.RestTemplate;

import java.io.File;
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.Paths;

public class SchemaGenerator {

    // URL нашего Dictionary Service
    private static final String DICTIONARY_SERVICE_URL = "http://localhost:8080/api/v1/schemas/country/json-schema";
    // Пакет, в котором будут созданы классы
    private static final String TARGET_PACKAGE = "com.yourcompany.person.model.generated";
    // Папка, куда будет сохранен сгенерированный файл
    private static final String TARGET_DIR = "target/generated-sources/java";

    public static void main(String[] args) throws IOException {
        System.out.println("Starting model generation from Dictionary Service...");

        // 1. Запрашиваем JSON Schema
        RestTemplate restTemplate = new RestTemplate();
        String jsonSchemaString = restTemplate.getForObject(DICTIONARY_SERVICE_URL, String.class);

        if (jsonSchemaString == null) {
            throw new IllegalStateException("Failed to fetch schema from: " + DICTIONARY_SERVICE_URL);
        }

        // 2. Настраиваем генератор
        JacksonModule jacksonModule = new JacksonModule();
        SchemaGeneratorConfig config = new SchemaGeneratorConfigBuilder(SchemaVersion.DRAFT_7, OptionPreset.PLAIN_JSON)
                .with(jacksonModule)
                // Указываем, что null-значения не должны включаться в схему
                .with(Option.NULLABLE_FIELDS_OMITTED)
                // Указываем, что нужно генерировать классы для "oneOf" и "allOf"
                .with(Option.FORBIDDEN_ADDITIONAL_PROPERTIES_BY_DEFAULT)
                .build();

        // 3. Генерируем код
        SchemaGenerator generator = new SchemaGenerator(config);
        // Важно: мы генерируем класс "Country" на основе полученной схемы
        String javaCode = generator.generateRawSchemaCode(jsonSchemaString);

        // 4. Сохраняем файл
        Path packagePath = Paths.get(TARGET_DIR, TARGET_PACKAGE.replace('.', '/'));
        Files.createDirectories(packagePath); // Создаем папки, если их нет

        Path targetFile = packagePath.resolve("Country.java");
        Files.write(targetFile, javaCode.getBytes());

        System.out.println("Successfully generated model: " + targetFile.toAbsolutePath());
    }
}
